# Proposal

## Why

У API сейчас есть только `GET /health`. Нужен один запрос, который собирает пользователя из двух JSON-источников и отдаёт страницу, отсортированную по `id`.

## What Changes

- Новый маршрут `GET /users`.
- Query: `page` и `limit`. Если параметра нет, он не целое число или число меньше 1, подставляется своё значение по умолчанию: `page=1`, `limit=10`. Корректный соседний параметр не сбрасывается.
- Ответ `200`: `{ items, total }`. `total` — число всех пользователей в первом источнике.
- Элемент `items`: `id`, `username` из первого источника; `addresses`, `teams`, `manager`, `salary` из второго, найденного по `id`.
- Список сортируется по числовому `id` по возрастанию, затем режется страница.
- Если `page` больше числа страниц, `items` пустой, `total` остаётся полным.
- Если второго источника для `id` нет, пользователь остаётся в списке и в `total`, а `addresses`, `teams`, `manager` и `salary` равны `null`.

Вне скоупа:

- Запись, изменение и удаление пользователей.
- Фильтры, поиск и сортировка не по `id`.
- Верхняя граница `limit`.
- Авторизация.
- Отдельный статус ошибки для некорректных `page` и `limit`.
- Сохранение хвостовых нулей у `salary`: в JSON `100.00` и `100` — одно число.

## Capabilities

### New Capabilities

- `users`: постраничная выдача пользователей, собранных из двух JSON-источников.

### Modified Capabilities

- Нет.

## Impact

- Новый маршрут `GET /users` на том же Fastify-приложении, что и `GET /health`.
- Два JSON-файла как вымышленные базы: пользователи (`id`, `username`) и сведения по `id` (`addresses`, `teams`, `manager`, `salary`).
- Новых npm-зависимостей нет. `GET /health` не меняется.
