# Design

## Context

Сейчас `src/app.ts` собирает Fastify и регистрирует только `GET /health`. `src/server.ts` только слушает. В `src/` нет handler, usecase и adapter. Зависимости смотрят внутрь: handler → usecase → port, adapter реализует port, `app.ts` связывает их. См. proposal.md, Why.

`tsconfig` включает только `src/` и не копирует JSON в `dist/`. Новых npm-пакетов нет.

## Goals / Non-Goals

**Goals:**

- Один usecase собирает страницу: читает всех пользователей, сортирует, режет страницу, для каждого id страницы берёт вторую запись.
- Handler приводит `page` и `limit` к числам до usecase.
- Оба JSON читаются с диска через adapter. Форму файла знает только adapter.

**Non-Goals:**

- Второй HTTP-сервер.
- Общий `shared/`: порт принадлежит одному usecase.
- Кэш между запросами и отдельное форматирование `salary`.
- Дедупликация `id`. Каждая строка первого файла — пользователь.

## Decisions

### Тот же Fastify в `src/app.ts`

`buildApp` создаёт adapter-ы, передаёт их в usecase и регистрирует handler. `GET /health` остаётся в `app.ts`. `server.ts` не меняется.

Альтернатива: отдельный `listen` для пользователей. Она режет один процесс на два сервера, а правило проекта — расширять приложение в `src/app.ts`.

### Четыре слоя одного действия

```
src/http/list-users.ts              query -> { page, limit }, ответ 200
src/usecase/list-users.ts           sort, slice, join
src/usecase/list-users.port.ts      listUsers, findProfile
src/domain/user.ts                  элемент списка, без HTTP и файлов
src/adapter/json/users-json.ts      data/users.json
src/adapter/json/user-profiles-json.ts
```

Два метода в одном port-файле, потому что оба нужны только этому usecase. Два adapter-а, потому что у файлов разная форма.

Альтернатива: один adapter сразу возвращает страницу. Тогда join и нарезка уезжают в код, который знает файлы.

### Срез до второй базы

Usecase читает весь первый файл, сортирует по числовому `id` по возрастанию и берёт срез `(page - 1) * limit` длиной `limit`. `total` — длина полного списка. Потом для каждого id среза вызывает `findProfile`.

Второй файл adapter читает один раз на запрос и отвечает на `findProfile(id)` из этой карты. Вызов по id остаётся в usecase, диск не открывается на каждый id.

Альтернатива: для каждого пользователя сразу читать вторую базу, потом сортировать и резать. Результат тот же, но чтение второй базы не зависит от страницы.

Нет записи → usecase ставит `addresses`, `teams`, `manager`, `salary` в `null`. Есть запись, но одного поля нет → это поле `null`, остальные как в файле.

### Файлы и cwd

Пути задаёт `app.ts`: `data/users.json` и `data/user-profiles.json` от `process.cwd()`. `npm run dev` и `npm start` запускаются из корня репозитория.

Альтернатива: путь от `import.meta.url`. После `tsc` файл оказывается под `dist/`, а JSON туда не копируется.

Форма:

```
users.json: [{ "id": 1, "username": "ann" }]

user-profiles.json: [{
  "id": 1,
  "addresses": [{ "country": "FI", "city": "Helsinki", "street": "Aleksanterinkatu" }],
  "teams": [{ "name": "Core", "department": "Engineering" }],
  "manager": "Ada Lovelace",
  "salary": 100
}]
```

В комплекте есть несколько строк, включая пользователя без второй записи, чтобы запрос к живому серверу показал и join, и `null`.

### Query в handler

Handler смотрит каждое значение отдельно. Вся строка — десятичные цифры и число ≥ 1 → это число. Иначе `page` становится 1, `limit` становится 10. Повтор query (`page=1&page=2`) не является такими цифрами и тоже уходит в значение по умолчанию. Usecase получает уже числа.

## Risks / Trade-offs

- [Каждый запрос читает оба файла целиком] → Для фикстур это нормально. Порт по-прежнему `findProfile(id)`, так что позже файл можно сменить на другой источник, не меняя handler.
- [Большой `limit` собирает длинный `items`] → Верхней границы нет: так задано поведение. Память ограничена размером JSON.
- [Правка JSON не видна, пока запрос не прочитает файл заново] → Чтение на каждый запрос, без кэша процесса. Рестарт не нужен.
- [Повтор `id` в первом файле даёт две строки] → Спека считает строки пользователями. Отдельной уникальности нет.

## Migration Plan

Маршрут новый. Старые запросы не меняются. Откат — убрать регистрацию `GET /users` и файлы этого действия.
